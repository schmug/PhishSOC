Analysis & disposition (confirmed)

All five disprove tests fail to refute. EXPLOITATION: a concrete, unauthenticated, attacker-reachable path exists (any inbound email to a provisioned mailbox). Attacker story

An external sender emails any provisioned mailbox in the deployment (inbound mail from untrusted senders is the product's core function) with a single attachment named e.g. `report.tlsrpt.gz` (or Content-Type `application/tlsrpt+gzip`) whose body is a small gzip bomb — a few hundred KB of gzip-compressed zeros that expands to 1GB+. Cloudflare Email Routing accepts it (under 25MB), PostalMime decodes the attachment bytes, isTlsRptReport() matches on the MIME/filename, and ingestTlsRptReport calls gunzip(), which streams the decompressed output into a single in-memory ArrayBuffer. Memory blows past the 128MB isolate limit and the runtime terminates the isolate before the 5MB cap check runs. Because email() re-throws (app.ts:180-185), Cloudflare retries delivery, so the same bomb re-triggers the OOM repeatedly, and concurrent requests sharing the isolate are collateral.

Trace / evidence

Attacker input -> sink trace: app.email() (app.ts:164) -> normalizeInbound/streamToArrayBuffer enforces only MAX_EMAIL_SIZE=25MB on the COMPRESSED stream (cf-routing.ts:22-31) -> receiveEmail (index.ts:1489) -> mailbox-existence check (index.ts:1496, satisfied by targeting any known mailbox) -> isTlsRptReport() returns true on attachment mimeType `application/tlsrpt+gzip` or filename `*.tlsrpt.gz` (ingest.ts:29-43) -> ingestTlsRptReport runs UNCONDITIONALLY (index.ts:1605, no enabled/opt-in gate, unlike RUF at 1621-1624) -> looksGz branch (ingest.ts:59,62) -> `const decompressed = await gunzip(raw)` (ingest.ts:64). gunzip (parser.ts:49-52) = `new Response(new Response(buf).body.pipeThrough(new DecompressionStream('gzip'))).arrayBuffer()`, which accumulates the ENTIRE decompressed output in memory. The size guard `decompressed.byteLength > TLSRPT_MAX_DECOMPRESSED_BYTES` (ingest.ts:65) only runs after gunzip resolves — the isolate OOMs mid-accumulation once decompressed bytes cross ~128MB, before the check is reached. gzip's ~1032:1 max ratio means a ~130KB gzip-of-zeros attachment (well under the 25MB envelope cap) yields ~134MB, exceeding the Workers 128MB isolate memory limit. Every guard on the path named and shown non-defeating.

Recommended fix

Make TLS-RPT decompression bounded, mirroring the DMARC sibling. Change parser.ts gunzip to accept a maxBytes parameter, read the DecompressionStream chunk-by-chunk via getReader().read(), accumulate a running byte total, and abort (return null) the instant it exceeds TLSRPT_MAX_DECOMPRESSED_BYTES — never materializing more than the cap. Then in ingest.ts, call `const decompressed = await gunzip(raw, TLSRPT_MAX_DECOMPRESSED_BYTES); if (decompressed === null) return { ingested: false, reason: "decompressed payload exceeds 5MB cap" };`. This rejects the bomb mid-stream with at most ~5MB resident instead of OOMing. Update the parser.ts:14-16 comment to reflect the now-true guarantee.

Severity calibration

Unauthenticated, internet-facing remote DoS. A ~130KB gzip bomb well under the 25MB envelope cap reaches the gunzip sink through the core inbound-mail path; the intended 5MB primary control is defeated by check-after-full-materialization, no opt-in gate, so no primary control holds. email()'s re-throw makes Cloudflare retry the same bomb (small-input amplification). DoS-only (no C/I; Cloudflare recovers isolates per-invocation) keeps it below critical.

Analysis & disposition (confirmed)

The root-cause defect is real and verifiable by JS semantics: for `&#xNN;`/`&#NN;` the parsed integer can exceed 0x10FFFF (e.g. `&#x110000;` = 1114112), `Number.isFinite` returns true (the regex guarantees a finite non-negative integer, so the guard is a no-op for bounds), and `String.fromCodePoint(1114112)` throws RangeError. It is attacker-reachable: the inbound email HTML body flows to `classifyEmail` (classification.ts:152) which calls `htmlToPlainText` OUTSIDE its own try block, and `measureAsync` re-throws (index.ts:397) so `runSecurityPipeline` throws. The candidate's specific 'DoS/crash' impact is defeated by a guard (the try/catch at receiveEmail index.ts:1711 catches the throw; Workers isolates also preclude a service-level DoS) — so this is NOT an exploitable denial of service. However, the same guard converts the crash into a security-pipeline FAIL-OPEN, which is itself a concrete exploitable consequence, so the finding is not fully refuted. Confirmed as a real, reachable, exploitable defect — but the accurate impact is a classifier/quarantine bypass, not DoS. Severity calibration is downstream.

Attacker story

On a phishing-triage backend, an anonymous external sender includes one out-of-range numeric HTML entity (e.g. &#x110000; or &#99999999;) anywhere in the message body. On receipt, classifyEmail calls htmlToPlainText before its own try/catch; decodeEntities calls String.fromCodePoint on the out-of-range value and throws RangeError. measureAsync re-throws, runSecurityPipeline aborts before verdict aggregation, and receiveEmail's catch leaves securityVerdict=null — the email is delivered to INBOX un-quarantined and the async deep-scan is skipped. Even an email that would otherwise fail SPF/DKIM/DMARC or trip URL/classifier heuristics is delivered unscanned.

Trace / evidence

shared/html-text.ts:47-52: `const code = Number.parseInt(body.slice(2),16); return Number.isFinite(code) ? String.fromCodePoint(code) : match;`. The replace regex `/&(#x[0-9a-f]+|#[0-9]+|[a-z]+);/gi` always yields at least one digit, so parseInt returns a finite non-negative integer and Number.isFinite is always true — it never rejects out-of-range values. Per ECMAScript, String.fromCodePoint throws RangeError when the argument is > 0x10FFFF; `&#x110000;` (1114112) and `&#99999999;` both exceed the max code point 0x10FFFF (1114111) and throw. Reachability trace: parsedEmail.html (attacker-controlled) -> bodyHtml -> classifyEmail (classification.ts:152, htmlToPlainText called before the try at line 172) -> throw -> measureAsync re-throws (security/index.ts:397) -> runSecurityPipeline throws (stages 6-7 abort, persistAll never runs) -> caught at receiveEmail (index.ts:1711), securityVerdict stays null, no moveEmail to QUARANTINE, email remains in INBOX. cases.ts:202 caller is inside its own try/catch (188-219); agent/index.ts:432/443 and client-side EmailPanel.tsx callers are unguarded but only cause localized (per-invocation / per-render) failures, not a service DoS.

Recommended fix

Range-check the parsed code point before String.fromCodePoint in decodeEntities (html-text.ts:47-52): replace `Number.isFinite(code)` with `Number.isInteger(code) && code >= 0 && code <= 0x10FFFF` for both the hex and decimal branches, returning the literal `match` otherwise (matching existing unknown-entity behavior). This neutralizes both the crash and the resulting pipeline fail-open. Analysis & disposition (confirmed)

The five disprove tests do not defeat it. EXPLOITATION: the send endpoints (POST /emails, /reply, /forward, and the agent/MCP send tool) are reachable by an authenticated mailbox user / compromised session, and checkSendRateLimit() and createEmail() are two independent DO RPCs with Worker-side awaits (storeAttachments/R2, getEmail, send-risk gate) between them, so concurrent requests all read the pre-insert SENT count before any insert lands. MITIGATION/PARSER-RUNTIME: there is no transaction, lock, or blockConcurrencyWhile linking the count read to the insert; the check is read-only and reserves nothing, and the synchronous nature of sql.exec is irrelevant because the vulnerable gap is between two separate round-trips, not inside one DO method — so the race holds even under fully serialized RPC delivery. The send-risk confirmation gate only covers risky sends and is separately satisfiable, so it does not close the window. BASELINE only affects severity (bounded abuse-control bypass), not exploitability. Confidence >80% that concurrent sends exceed the quota.

Attacker story

An authenticated user (or attacker with a stolen session/token) who wants to exceed the outbound anti-abuse quota scripts, say, 100 simultaneous POST /emails requests to their mailbox. Because each request reads the SENT-folder count before any of the inserts commit, all 100 pass the 20/hr check at the same low count, then all 100 createEmail inserts land and all 100 sendEmail deliveries are dispatched, blowing past the intended 20/hr and 100/day caps in a single burst and defeating the outbound spam/abuse throttle.

Trace / evidence

Trace: attacker-controlled concurrent POST /api/v1/mailboxes/:id/emails (and /reply, /forward, agent tool). In workers/routes/send-email.ts:78-82: `const rateLimitError = await stub.checkSendRateLimit(); if (rateLimitError) return 429; const attachmentData = await storeAttachments(...); await stub.createEmail(Folders.SENT, ...)`. checkSendRateLimit (workers/durableObject/index.ts:855-879) runs two synchronous COUNT(*) reads over folder_id=Folders.SENT and returns null when cnt<20/100 — it writes nothing and reserves no slot. createEmail (index.ts:883+) is a distinct RPC that performs the INSERT. Between the two RPCs the Hono handler (running in the Worker, which has no DO input gate) awaits storeAttachments (R2 puts). With N requests fired concurrently: every checkSendRateLimit returns before any createEmail is issued (each request only calls createEmail after finishing storeAttachments), so all N read the same stale count and pass; then all N inserts land, yielding up to (starting_count + N) SENT rows against a 20/hr cap. reply-forward.ts:70-78 and 178-186 and lib/tools.ts:461,581 repeat the identical check-then-act split. grep confirms no blockConcurrencyWhile and no combined atomic method in any send path. The real outbound delivery (sendEmail via c.executionCtx.waitUntil) fires only after the check passes, so bypassing the check produces real extra outbound emails.

Recommended fix

Make the reservation atomic in a single no-await DO method. Add a DO method (e.g. reserveSendSlotAndCreate) that, within one synchronous invocation (no await between read and write), runs the COUNT(*) checks and, if under the limit, performs the createEmail INSERT — since a single DO method with no internal await runs to completion atomically, this removes the interleaving window. Callers then invoke that one RPC instead of separate checkSendRateLimit()+createEmail() calls. Storing attachments (R2) should still happen before the atomic call, but the count check must be re-evaluated inside the same synchronous method that inserts. Alternatively maintain an atomically-incremented rolling counter guarded inside the insert method and reject (throw / return an error) when the window count would exceed 20/hr or 100/day.

Severity calibration

Real TOCTOU: the check reserves nothing and is a separate DO RPC from the insert, so N concurrent authenticated sends all pass the same stale count and produce (start+N) real outbound emails, defeating the 20/hr-100/day throttle in one burst. DOWNGRADED medium->low (internal-no-boundary): the attacker only amplifies an action they are already authorized to perform (send from any mailbox by documented design); no privilege/trust boundary between principals is crossed, CF Access holds and a coarse provider-level throttle still backstops. Kept (not dropped) because it produces real extra outbound email and is concretely reachable.
